## 1. 为什么下一阶段应该做这个

LegacyPilot 已经具备三类任务模式、真实执行 API、持久化任务状态、结构化产物、源码证据、审批与恢复能力，也已经有可操作的 Web 工作台。当前最大的短板不是缺少更多 Agent 概念，而是这些能力还没有形成一套面试者可以在新环境中稳定复现、让面试官在 10 分钟内看懂的产品闭环。

本阶段要证明四件事：

1. **产品能力：** 用户只需描述问题，就能完成 `EXPLAIN`、`ANALYZE` 和 `CHANGE` 三类真实任务；
2. **Agent 能力：** 不同意图产生不同计划，计划执行过程可观察，失败后可以继续；
3. **工程能力：** 长任务异步执行、状态持久化、幂等、重连、取消、重试和自动化测试完整；
4. **安全能力：** 源码访问受限，变更必须审批，开发者与审批人职责分离，所有结论可回溯到证据。

这比继续增加一个新模型或新工具更适合作为求职作品：它能把产品判断、Agent 设计、后端工程、前端交互、安全治理和质量保障放在同一条演示路径中。

## 2. 完成定义

本阶段只有同时满足以下条件才算完成：

- 在一台新机器上，从仓库检出到打开可用工作台不超过 10 分钟，并提供一条主启动命令；
- Web 中可真实完成至少一个 `EXPLAIN`、一个 `ANALYZE` 和一个需要审批的 `CHANGE` 任务；
- 启动执行的 API 立即返回任务已受理，长任务在后台运行，不占用浏览器请求；
- 页面优先通过服务端事件流显示步骤、日志摘要和状态变化，断线后自动重连，并保留轮询降级；
- 结论、计划、变更、验证和风险都能回链到 revision、路径、符号、行号或受控源码片段；
- 源码读取接口阻止绝对路径、路径穿越、符号链接越界和非当前 revision 访问；
- `CHANGE` 在执行写操作前展示计划与变更摘要，并由独立审批身份批准或拒绝；
- 运行中止、服务重启或浏览器刷新后，任务不会丢失，用户能继续、重试或取消；
- 核心 API、权限边界和三条浏览器主路径有自动化测试；
- 有一份 8–10 分钟演示脚本、架构说明、已知限制和可复现的演示证据。

## 3. 目标用户工作流

### 3.1 讲解业务：`EXPLAIN`

用户输入“请讲清楚转账业务是如何实现的”。系统识别为只读讲解，先定位入口和核心领域对象，再沿调用关系解释业务流程，最终输出分层说明和源码证据，不创建补丁，也不触发审批。

### 3.2 分析需求：`ANALYZE`

用户输入“如果增加单笔转账限额，需要修改哪些地方，有什么风险”。系统生成分析计划，读取相关代码与测试，输出影响范围、实现建议、风险、待确认问题和证据，不修改工作区。

### 3.3 修改代码：`CHANGE`

用户确认需求后创建变更任务。系统规划实现步骤、生成受控修改，在外部写操作前暂停；页面展示计划、差异与风险，独立审批人批准后继续，最终运行 Maven 验证并生成审计报告。

### Issue 43 — 实时运行事件流与断线恢复

**实施状态（2026-09-07）：** 真实验收完成。服务端基于持久化、脱敏 Trace 提供按 run 订阅的 SSE，事件包含连续序号、时间、阶段、状态、受控摘要与命令 correlation ID；`Last-Event-ID` 只补发缺失事件。浏览器测试通过 Demo 故障接口真实关闭活动 `SseEmitter`，观测到轮询降级、携带非零 `Last-Event-ID` 自动重连，并逐项比对从首事件到 `run.completed` 的序号无重复、无缺失；独立场景也验证 SSE 完全不可用时任务仍由轮询完成。

#### 工作内容

- 提供按 run 订阅的 Server-Sent Events（SSE）接口；
- 事件至少包含序号、时间、阶段、状态、用户可读摘要和 correlation ID；
- 支持 `Last-Event-ID`，重连时先补齐缺失事件，再继续实时推送；
- Web 将实时事件映射为步骤进度、状态提示和可展开的运行记录；
- 网络、代理或浏览器不支持事件流时自动降级为现有轮询；
- 事件输出沿用敏感信息脱敏策略，不直接推送模型原始密钥、完整环境变量或未经授权的源码。

#### 验收条件

- 正常执行时，用户无需刷新即可看到阶段变化；
- 主动断网再恢复后，不丢事件、不重复展示最终结果；
- SSE 不可用时任务仍能通过轮询完成；
- 事件顺序、权限、断线补发和脱敏有自动化测试。

### Issue 44 — 安全源码证据与文件查看接口

**实施状态（2026-09-06）：** 工程实现完成。服务端新增 project + pinned revision + 仓库相对路径绑定的源码读取 API，直接读取不可变 Git blob，不依赖可能漂移的当前 checkout；绝对路径、任何 `..`、符号链接 blob、非 UTF-8/二进制、超限文件、超限上下文和错误 revision 均失败关闭。响应同时提供原始 blob、精确证据行和展示片段三类 SHA-256。只读 artifact 自动携带 excerpt SHA-256，Web 以 revision、精确行哈希和摘录内容联合校验，支持证据行定位、上下文展开、受控全文与路径复制。允许和拒绝均写入仅含主体、项目、revision、路径、范围、结果与原因的元数据审计日志，不复制源码正文。

### Issue 45 — CHANGE 差异、验证与独立审批工作台

**实施状态（2026-09-06）：** 工程实现完成。服务端新增 CHANGE 决策包 API，基于受管 workspace 与 Git `HEAD` 生成文件级、行级差异，并统一返回计划版本、预计影响文件、风险、策略检查、服务端 action/plan digest、审批身份及编译、测试、静态检查和覆盖率门禁状态。审批提交会再次校验当前 checkpoint 的双 digest，计划或动作变化后旧请求以冲突失败；开发者与审批人仍强制职责分离。Web 在同一工作台回答“改了什么、为什么改、谁批准、验证是否通过”，拒绝必须填写理由，随后消费拒绝决定并终止受治理动作，同时提示通过新 CHANGE 任务重新规划。

#### 工作内容

- 为 `CHANGE` 增加文件级和行级差异视图；
- 将执行计划、预计影响文件、策略检查、审批摘要和风险放在同一决策界面；
- 审批提交继续使用服务端生成的 action/plan digest，页面不自行推导可信摘要；
- 独立展示测试、编译、静态检查和覆盖率结果；
- 支持拒绝理由，并在拒绝后明确展示任务的终止或重新规划路径；
- 把开发者 JWT 与审批人 JWT 的会话、权限错误和过期处理做成可理解的用户提示。

#### 验收条件

- 开发者身份不能批准自己需要职责分离的动作；
- 审批人批准的 digest 与随后执行的动作完全一致，计划变化后旧审批失效；
- 用户能在一个页面回答“改了什么、为什么改、谁批准、验证是否通过”；
- 没有批准时不会发生受治理的写操作。

### Issue 46 — 取消、重试、失败恢复与可操作错误

**实施状态（2026-09-07）：** 真实验收完成。除模型失败重试和安全点取消外，Playwright 会对真实 Java 服务进程执行强制终止并由外部 supervisor 重启；同一 H2、checkpoint、request、lease 和 command 数据恢复后，同一任务成功结束且原 command 的 worker claim 数至少为 2。验证恢复场景先写入确定性编译错误并运行真实网络隔离 Maven，页面显示“验证失败”；重新规划会产生新计划和新 action digest，旧审批不复用，第二位审批人重新批准修复动作后 Maven 通过。运行时租约在长验证期间按 TTL/3 心跳续租；用户取消与后台完成并发时，以已持久化的 `CANCELLED` 为准，不再产生后台并发更新失败。

#### 工作内容

- 增加请求取消、从安全 checkpoint 重试和继续运行的 API；
- 区分用户取消、模型失败、工具失败、策略阻断、验证失败和基础设施失败；
- 页面根据失败类型只显示合法动作，例如“重试当前步骤”“重新规划”“等待审批”或“查看诊断”；
- 对不可安全重放的动作显示人工复核，不提供误导性的自动重试；
- 所有状态改变使用乐观并发或版本校验，防止两个浏览器互相覆盖；
- 保留每次 attempt，重试不覆盖旧证据。

#### 验收条件

- 用户可取消排队中任务和正在安全阶段执行的任务；
- 重试产生可审计的新 attempt，不重复已确认成功的外部动作；
- 两个页面同时操作时，过期请求得到明确冲突提示；
- 服务重启、模型超时和 Maven 失败都有可演示的恢复路径。

## 5. 执行顺序与阶段关卡

| 阶段 | 工作包 | 可见成果 | 进入下一阶段的门槛 |
| --- | --- | --- | --- |
| A. 可启动 | Issue 41 | 一键启动的真实工作台 | 新环境 10 分钟内可用，Demo 身份边界通过 |
| B. 可长期运行 | Issues 42–43 | 后台执行与实时进度 | 幂等、重启恢复、断线重连全部通过 |
| C. 可相信 | Issues 44–45 | 源码、差异、验证和审批证据 | 路径安全、职责分离、digest 绑定通过 |
| D. 可恢复 | Issue 46 | 取消、重试和失败处理 | 故障注入不会丢任务或重复危险动作 |
| E. 可交付 | Issues 47–48 | 自动验收和面试演示包 | 三次稳定演示，全部发布硬门槛通过 |

不要同时铺开全部工作。每个阶段通过验收后再开始下一阶段；否则优先修复当前闭环，而不是把问题推迟到最后集成。

## 6. 推荐的面试演示顺序

1. 用一条命令启动系统，打开真实项目工作台；
2. 创建 `EXPLAIN`：“请解释转账业务的完整调用链”，展示不同于代码修改的只读计划；
3. 点击结论，跳到 revision 固定的源码证据；
4. 创建 `ANALYZE`：“增加单笔转账限额会影响哪些代码和测试”，展示影响面、风险与待确认项；
5. 将确认后的需求作为 `CHANGE` 执行，展示计划、代码差异和暂停审批；
6. 切换独立审批人批准，继续运行 Maven 验证并查看最终报告；
7. 在另一个任务执行中重启服务，展示任务恢复与事件续传；
8. 最后打开审计证据，说明每项结论和动作如何被验证。

演示重点不是“模型一次生成了多少代码”，而是“一个不完全可靠的模型，如何被工程系统约束成可观察、可审批、可恢复、可验证的 Agent”。

## 7. 明确不做

- 不做无限多轮通用聊天和社交式消息系统；
- 不做多 Agent 编排、插件市场、IDE 插件或 Kubernetes；
- 不做多人协同项目管理和通用 SaaS 租户系统；
- 不把源码全文接口开放成任意文件服务器；
- 不为了演示绕过 Policy、职责分离、revision 或审计约束；
- 不把 route mock、预录结果或 reference solution 当成真实运行证据；
- 不在本阶段顺带重写检索、模型网关或整个前端技术栈。

## 8. 与模型质量工作的关系

当前 20 题真实模型结果为 9/20（45%），低于既定 70% 发布门槛。这是需要公开保留的独立事实。

本阶段允许使用固定的、已验证的 Banking Demo 场景证明产品闭环，但必须同时做到：

- 不声称固定演示通过等于通用模型质量达标；
- 演示结果记录模型、Prompt、revision 和运行环境；
- 20 题质量 Dashboard 继续可访问，并明确标注当前结果；
- 产品化工作完成后，再以失败分类数据决定优化 Prompt、检索还是模型，而不是盲目调参。

## 9. 每个 Issue 的统一交付清单

每个工作包完成时都应包含：

- 用户可感知的行为变化；
- API 或状态契约及向后兼容说明；
- 正常路径、失败路径和安全负向测试；
- 运行、恢复和排障说明；
- 可从页面或报告回溯的验收证据；
- 未解决风险与下一 Issue 的输入条件。

## 10. 第一个执行切片

建议从 Issue 41 开始，只交付以下最小闭环：

1. 一条主启动命令；
2. 自动创建 Banking Demo 项目；
3. loopback-only 的开发者与审批人 Demo 身份；
4. 服务、数据库、模型和项目 revision 的启动前检查；
5. 一条真实 `EXPLAIN` 任务成功完成并在 Web 中显示证据。

这个切片通过后，再进入异步执行改造。这样可以先建立后续所有浏览器测试和面试演示都依赖的稳定底座。
